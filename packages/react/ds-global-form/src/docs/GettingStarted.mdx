# Getting Started with Forms

The form system provides a `Form` wrapper and a `Field` router. Built-in fields provide form binding, validation, error display, and accessibility; custom components supply their own. It integrates with [react-hook-form](https://react-hook-form.com/) and uses CSS subgrid for layout.

## Installation

```bash
bun add @canonical/react-ds-global-form @canonical/styles
```

### Import the styles

Two stylesheets are required, imported in your application's root stylesheet:

```css
/* 1. The global Pragma styles — CSS reset, typography baseline, and the design
      tokens (colour, spacing, surfaces, states) every component reads. */
@import url("@canonical/styles");

/* 2. The form styles — input chrome, field layout, and per-component styles. */
@import url("@canonical/react-ds-global-form/dist/esm/index.css");
```

Both are needed: the form stylesheet styles the inputs and field layout, but it
consumes the design tokens defined by the global `@canonical/styles` — without
the global import the form renders unstyled (missing colours, spacing, and the
grid). The form package also builds on `@canonical/react-ds-global`.

## Basic form

A form needs a grid parent, a `Form` wrapper, and one or more `Field` components:

### Why a grid parent?

`Form` renders as a CSS subgrid (`grid-template-columns: subgrid; grid-column: 1 / -1`). It inherits column tracks from its parent grid rather than creating its own. This means the form's fields align with the page grid — labels, inputs, and error messages participate in the same column structure as surrounding content.

## The Form component

`Form` wraps children in a react-hook-form [`FormProvider`](https://react-hook-form.com/docs/formprovider). It has two modes:

**Internal mode** (simple) — `Form` creates its own `useForm` instance. Pass
`onSubmit`, and optionally `defaultValues` and a validation `mode`. Use this for
a self-contained form where you don't need direct access to the form state.

```tsx
<Form
  onSubmit={handleSubmit}
  defaultValues={{ name: "Ada", email: "" }}
  mode="onBlur"
>
  <Field name="name" inputType="text" label="Full name" />
  <Field
    name="email"
    inputType="text"
    label="Email address"
    registerProps={{ required: "Email is required" }}
  />
  <Button type="submit">Send</Button>
</Form>
```

<Canvas of={Stories.InternalMode} />

**External mode** (advanced) — you create the `useForm` instance and pass it as
`methods`. Because you own it, you can read `formState` (e.g. `isSubmitting`) and
call its methods (`reset`, `setValue`, `watch`, …). Reach for this when a submit
is async, when the form state is shared across components, or for multi-step /
wizard forms that keep one instance across steps.

```tsx
import { useForm } from "react-hook-form";

function SignupForm() {
  const methods = useForm({
    mode: "onBlur",
    defaultValues: { name: "", email: "" },
  });
  const {
    reset,
    formState: { isSubmitting },
  } = methods;

  const onSubmit = async (data) => {
    await api.createUser(data); // your async call
    reset(); // clear back to defaultValues after success
  };

  return (
    <Form methods={methods} onSubmit={onSubmit}>
      <Field name="name" inputType="text" label="Full name" />
      <Field
        name="email"
        inputType="text"
        label="Email address"
        registerProps={{ required: "Email is required" }}
      />
      <Button type="submit" disabled={isSubmitting}>
        {isSubmitting ? "Saving…" : "Send"}
      </Button>
    </Form>
  );
}
```

<Canvas of={Stories.ExternalMode} />

When you pass `methods`, `Form`'s own `defaultValues` and `mode` props are
ignored — configure those on your `useForm` call instead.

Text, number, date and select fields render representable RHF defaults in server
markup. A select default is representable only when its option is present. An
explicit native `defaultValue` takes precedence in that markup. During hydration,
an early browser edit is adopted if the form value has not changed since the
field's client render; `reset` subsequently uses RHF defaults. A form mutation
or equal-value reset before client initialization cannot be distinguished from
an unchanged default: hosts needing conflict safety must coordinate hydration
and retain their own revision or draft. For `valueAsDate`, a Date default renders
its UTC calendar date while RHF retains its original time until an edit or reset.
Textarea and checkbox defaults and early edits do not have this hydration support.

Native-bound fields are RHF-owned: use `defaultValues`, `setValue`, `reset` and
`registerProps.onChange` rather than a separate native `value`/`onChange` pair.
React can display a native `value` without synchronizing RHF's submitted value;
RHF replaces native `onChange`. Use a custom field with RHF `Controller` or
`useController` for externally controlled widgets.

RHF registers during render, so a suspended or abandoned render can expose its
native registration rules before commit. Use a resolver or submit flow and server
validation for authoritative validation.

## Understanding react-hook-form

This library is a thin layer over [react-hook-form](https://react-hook-form.com/)
(RHF, `^7.71`). `Form` provides the [`FormProvider`](https://react-hook-form.com/docs/formprovider)
and built-in fields bind to RHF for you — but **the form state, validation, submission, and everything beyond a
single field is react-hook-form's API, not this library's.** To build a real
form you should read the RHF docs; this section is a map of the surface you will
use, with the pieces this library already wires up called out.

> This library re-exports nothing from RHF. Import RHF hooks
> (`useForm`, `useFormContext`, `useController`, `useFieldArray`) directly from
> `"react-hook-form"`.

### `useForm` — the form instance

You only call `useForm` yourself in **external mode** (passing `methods` to
`Form`); in internal mode `Form` calls it for you from its `defaultValues`/`mode`
props. Its most-used options ([full reference](https://react-hook-form.com/docs/useform)):

- `mode` — when validation first runs: `"onSubmit"` (default), `"onBlur"`,
  `"onChange"`, `"onTouched"`, or `"all"`.
- `defaultValues` — the initial values (an object, or an async function that
  returns one). Also what `reset()` restores to.
- `values` — externally-controlled values that re-sync the form when they change.
- `resolver` — plug in schema validation (zod/yup/valibot…); see below.
- `reValidateMode`, `criteriaMode`, `shouldUnregister`, `delayError` — finer control.

`useForm` returns the **methods object** (also what `useFormContext()` returns
inside a `Form`): `register`, `handleSubmit`, `watch`, `getValues`, `setValue`,
`reset`, `resetField`, `setError`, `clearErrors`, `trigger`, `setFocus`,
`unregister`, `getFieldState`, `control`, and `formState`.

### `formState` — reacting to the form

[`formState`](https://react-hook-form.com/docs/useform/formstate) is how you read
what the form is doing. The fields you will reach for most:

- `errors` — per-field validation errors (this library renders these for you).
- `isSubmitting` — true while an async `onSubmit` runs (disable the submit button).
- `isValid` / `isDirty` — whether the form passes validation / differs from defaults.
- `isSubmitSuccessful`, `submitCount`, `touchedFields`, `dirtyFields`.

### Validation rules (`registerProps`)

A `Field`'s `registerProps` is RHF's
[validation rules](https://react-hook-form.com/docs/useform/register) object,
passed straight to `register`: `required`, `min`, `max`, `minLength`,
`maxLength`, `pattern`, and `validate`, plus the value transforms `valueAsNumber`,
`valueAsDate`, and `setValueAs`. See [Validation](#validation) below for a live
example.

RHF merges registrations by field name: removing a `registerProps` key does not
reliably remove an earlier rule or callback. Explicitly set the key to `undefined`
or `required: false` when the field exclusively owns it. In particular, changing
`isOptional` from optional to required and back does not remove the previously
registered required rule. Explicitly supply `registerProps={{ required: false }}`
when making an exclusively owned field optional. Clearing a rule on a shared name
affects its other registrations.

Same-name checkbox group ownership is unresolved. Native required validity can
disagree with RHF when another checkbox is checked; disabled registration order can
affect submitted values; shared errors can produce duplicate alerts and inconsistent
required announcements; and suspended optionality changes can affect validation
before commit. Prefer one `ChoicesField` for an RHF-owned group, and independently
verify native and no-JavaScript requirements. Checkbox defaults are not rendered
into server HTML and an early checkbox edit may be lost during hydration.

### Schema validation (optional)

For a single source of truth you can validate against a schema instead of
per-field rules, via a `resolver`. This needs two extra packages —
`@hookform/resolvers` and a schema library such as `zod` — which are **not**
bundled with this library:

```bash
bun add @hookform/resolvers zod
```

```tsx
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { z } from "zod";

const schema = z.object({
  name: z.string().min(1, "Name is required"),
  email: z.string().email("Enter a valid email"),
});

const methods = useForm({
  resolver: zodResolver(schema),
  defaultValues: { name: "", email: "" },
});
// <Form methods={methods} …> — no per-field registerProps needed
```

### Beyond the basics

For repeating groups of fields (e.g. a list of contacts) use RHF's
[`useFieldArray`](https://react-hook-form.com/docs/usefieldarray); for
custom/controlled inputs use [`useController`](https://react-hook-form.com/docs/usecontroller)
(this library already uses it internally for controlled fields — see
[Creating Custom Fields](?path=/docs/global-form-guides-creating-custom-fields--docs)).
When in doubt, the [react-hook-form documentation](https://react-hook-form.com/docs)
is the authoritative reference for everything the form can do.

## The Field component

`Field` is a type-safe router. The `inputType` prop selects the underlying input component, and TypeScript enforces that only valid props for that input type are accepted:

<Canvas of={Stories.InputTypes} />

Built-in fields use internal wrappers and binding that provide:

- Label rendering and `<label>` association
- Description text (the `description` prop)
- Error message display when validation fails
- ARIA attributes (`aria-labelledby`, `aria-describedby`, `aria-errormessage`, `aria-invalid`)
- Form registration via react-hook-form

Custom components are rendered directly and provide their own binding and presentation.

By default, fields are required. Mark a field as optional with the `isOptional` prop.

## Middleware

Middleware wraps the input component to add cross-cutting behaviour. Each middleware is a function that receives a component and returns an enhanced component:

```tsx
import { Field, addRESTOptions, addRESTValidation } from "@canonical/react-ds-global-form";

// Create middleware outside render, or use useMemo for changing configuration.
const countries = addRESTOptions("/api/countries", {
  transformData: (data) => data.countries.map(c => ({ value: c.code, label: c.name })),
});
const usernameValidation = addRESTValidation("/api/check-username", {
  debounceWait: 300, minLength: 3,
});

// Fetch options from an API
<Field
  name="country"
  inputType="select"
  label="Country"
  options={[]}
  middleware={[countries]}
/>

// Advisory remote check with debouncing
<Field
  name="username"
  inputType="text"
  label="Username"
  middleware={[usernameValidation]}
/>
```

Middleware composes as an array. The first middleware in the array wraps outermost; the last wraps innermost (closest to the input). Custom middleware follows the same signature: `(Component) => EnhancedComponent`.

Keep middleware function identities stable between renders; changing one remounts
the composed input. StrictMode may call factories more than once, so factories
must not perform side effects during composition.

`addRESTValidation` is advisory: pending or failed requests do not block
submission, and RHF validation or submission can clear even a completed remote
error. Validate authoritatively in the resolver or submit flow and on the server.
Superseded requests are cancelled, stale results ignored and unrelated errors
preserved. Network or response-extraction failures do not establish validity.

When a single select initially has options but no form or native default, the
browser's first enabled option becomes the RHF value. Supply an empty placeholder
option if an explicit choice is required. Dynamic options are not reconciled to
the form value: when options arrive or change, the browser's selection and RHF's
value may differ. Coordinate the choice list and form value in the host.

When a select's RHF value contains unavailable or disabled options, the field
marks the control invalid and displays a warning while retaining the form value.
The warning does not block submission. If a selected single option disappears,
the browser may display and submit a fallback while RHF retains and submits the
old value. A disabled selected option may be omitted from native `FormData`.
Before hydration, missing defaults likewise cannot be represented in native
markup, and the browser may choose a fallback; early edits and form defaults can
conflict. Do not rely on the warning to prevent these discrepancies: ensure the
choices and defaults agree before rendering and reject unavailable or disabled
values in the resolver or submit flow and on the server. For multiple selects,
`null`, `undefined` and an empty string render no selection; the RHF value is
retained until an edit produces an array. Native multiple-select values follow
DOM order; RHF retains the form's array order until an edit.

## Error state styling

Form error states use a CSS class-based mechanism rather than modifier channel variables. When a field has a validation error:

1. The `Wrapper` component adds a `.danger` class to the field container
2. CSS targets `.danger > .payload .ds.input.chrome` to shift the border to the error color
3. The error message renders below the input with `aria-errormessage` association

This is a deliberate architectural choice. Form validation states are binary (valid/invalid) and driven by react-hook-form, not by semantic modifier context. The form error mechanism and the modifier system are complementary but independent.

## Custom fields

For inputs not covered by the built-in types, use `inputType="custom"` with a `CustomComponent`:

```tsx
import { Field } from "@canonical/react-ds-global-form";
import { MyDateRange } from "./MyDateRange";

<Field
  name="period"
  inputType="custom"
  CustomComponent={MyDateRange}
  label="Date range"
/>
```

Custom components accept at least a `name` and provide any binding, labels, errors, conditional display and middleware they need. See the [Creating Custom Fields](?path=/docs/global-form-guides-creating-custom-fields--docs) guide for implementation details.
