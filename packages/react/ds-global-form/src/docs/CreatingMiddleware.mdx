# Creating Middleware

Middleware lets you extend field behaviour without modifying field components. It is the form system's mechanism for cross-cutting concerns: fetching options from an API, validating against a server, reacting to changes in other fields, adding analytics, or injecting loading states.

Transforming the value between what the user sees and what the form submits is **not** one of them — see [Why masking is not middleware](#why-masking-is-not-middleware) below.

This guide covers the middleware model, the two built-in middleware functions, and how to write your own.

## How middleware works

A middleware is a higher-order component (HOC) factory. It receives the input component and returns an enhanced version of it. The enhanced component can add state, side effects, or transformed props — then renders the original component with whatever modifications it needs.

```typescript
// The middleware type signature
type Middleware<ComponentProps> = (
  Component: React.ComponentType<ComponentProps>
) => React.ComponentType<ComponentProps>;
```

Middleware is applied at the `Field` level through the `middleware` prop, which takes an array:

```tsx
<Field
  name="country"
  inputType="select"
  label="Country"
  options={[]}
  middleware={[addRESTOptions("/api/countries")]}
/>
```

Middleware can be created inline, as above. The field keeps one instance across re-renders, so the input neither remounts nor repeats its requests; see [Settings that change](#settings-that-change).

### Where middleware sits in the component tree

Middleware wraps the input component _inside_ the Wrapper. The composition order is:

```
Field
  └─ Wrapper (label, description, error, ARIA)
       └─ Middleware[0]        ← outermost middleware
            └─ Middleware[1]   ← next middleware
                 └─ ...
                      └─ bindField(Input)  ← the RHF-bound field
                           └─ Input component
```

The first middleware in the array is the outermost wrapper. Each middleware receives the result of the next one as its `Component` argument. The innermost middleware receives the **bound** component — `bindField(Input)`, not the presentational input itself.

That distinction matters. `bindField` is where `register()` or `useController` runs, so `value`, `onChange` and the element `ref` are all created *below* every middleware. Middleware sees the props going into the binding — `name`, `registerProps`, the ARIA props — and can add to them; it cannot intercept the value on its way out, and it never has the DOM node.

This ordering is handled by `withWrapper`, which reduces the array from the right:

```typescript
middleware.reduceRight((Accumulated, hoc) => hoc(Accumulated), InputComponent);
```

## Built-in middleware

The form package ships two middleware for common API integration patterns.

### addRESTOptions

Fetches options from an API endpoint and injects them as the `options` prop. Useful for select, combobox, and choice fields whose options come from a server.

```tsx
import { Field, addRESTOptions } from "@canonical/react-ds-global-form";

<Field
  name="country"
  inputType="select"
  label="Country"
  options={[]}
  middleware={[
    addRESTOptions("/api/countries", {
      // HTTP method (default: "GET")
      method: "GET",

      // Custom headers for the request
      headers: { Accept: "application/json" },

      // Transform the API response into the { value, label } format
      // that select/combobox/choices expect
      transformData: (data) =>
        data.countries.map((c) => ({
          value: c.code,
          label: c.name,
        })),
    }),
  ]}
/>
```

The field keeps its normal markup while the options load: it is disabled, marked `aria-busy`, and has no options. If the request fails, the failure is set as the field's error with `setError`, so it shows where the field shows any other error. Once the data arrives, the field renders with the fetched options. The field stays enabled, so the user can see the error and the form stays usable. The fetch is keyed on the URL: re-rendering the field with a middleware created inline fetches nothing, and a different URL fetches the new options without remounting the field, dropping any answer still on its way for the previous URL. The request is aborted when the field unmounts. Its error type is `restOptions`, so it only ever clears its own error.

### addRESTValidation

Validates the field value against an API endpoint with debouncing. Useful for checking uniqueness (usernames, email addresses) or applying server-side validation rules.

```tsx
import { Field, addRESTValidation } from "@canonical/react-ds-global-form";

<Field
  name="username"
  inputType="text"
  label="Username"
  middleware={[
    addRESTValidation("/api/check-username", {
      // HTTP method (default: "POST")
      method: "POST",

      // Minimum input length before validation triggers (default: 3)
      minLength: 3,

      // Debounce wait in milliseconds (default: 300)
      debounceWait: 300,

      // Format the request body (default: { value })
      bodyFormatter: (value) => ({ username: value }),

      // Extract the error message from a failed response
      errorExtractor: async (response) => {
        const data = await response.json();
        return data.message;
      },
    }),
  ]}
/>
```

The middleware watches the field value via `useFormContext`. When the value changes and meets the minimum length, it debounces and sends a request. If the server returns a non-OK response, the middleware calls `setError` on the field with the error type `restValidation`, which triggers the `.danger` error state. If the server returns OK, or the value becomes shorter than the minimum, it clears the error it set, leaving errors from the field's rules in place. A request that fails to complete says nothing about the value, so the previous message stays. Each change cancels the pending timer and aborts the request in flight, so only the answer for the latest value can set or clear the error; unmounting the field does the same.

The check is also added to the field's `validate` rules, under the name `restValidation`, next to any `validate` rules the field already has. Submitting runs the rules again, so a value the server rejected blocks the submit instead of having its error cleared. A value submitted before its check has run waits for the answer, which the typing and the submit share, so they send one request.

## Writing custom middleware

### The factory pattern

Custom middleware follows a factory pattern: an outer function accepts configuration, and returns the actual middleware HOC.

```typescript
import { createElement } from "react";
import type { Middleware } from "@canonical/react-ds-global-form";

/**
 * Middleware factory that adds analytics tracking to a field.
 * Logs an event whenever the field value changes.
 */
function withAnalytics(eventName: string): Middleware<any> {
  // Return the middleware HOC
  return (WrappedComponent) => {
    // Return the enhanced component
    return function AnalyticsComponent(props) {
      const { name } = props;
      const { watch } = useFormContext();
      const value = watch(name);

      useEffect(() => {
        if (value !== undefined) {
          trackEvent(eventName, { field: name, value });
        }
      }, [value, name]);

      // Render the original component unchanged
      return createElement(WrappedComponent, props);
    };
  };
}
```

The three levels serve different purposes:
- **Factory** (`withAnalytics(eventName)`) — captures configuration.
- **HOC** (`(WrappedComponent) => ...`) — receives the component to wrap. Called during middleware composition.
- **Enhanced component** (`function AnalyticsComponent(props)`) — renders on every update. This is where hooks, state, and side effects live.

A field compares a plain middleware by identity. Called inline, `withAnalytics(eventName)` makes a new middleware on every render, so the field composes a new component and the input remounts. Build the middleware with `createMiddleware` to avoid that.

### Settings that change

`createMiddleware` turns the HOC into a factory taking settings. The HOC receives a `useSettings` hook alongside the component, and the field compares middleware from the same factory by their HOC, so an inline call keeps the same component and `useSettings` returns the settings of the newest call. Key effects on the settings that should restart them, as `addRESTOptions` keys its fetch on the URL.

```typescript
import { createElement, useEffect } from "react";
import { useFormContext } from "react-hook-form";
import { createMiddleware } from "@canonical/react-ds-global-form";

const withAnalytics = createMiddleware<string>(
  (WrappedComponent, useSettings) =>
    function AnalyticsComponent(props) {
      const eventName = useSettings();
      const { watch } = useFormContext();
      const value = watch(props.name);

      useEffect(() => {
        if (value !== undefined) {
          trackEvent(eventName, { field: props.name, value });
        }
      }, [eventName, value, props.name]);

      return createElement(WrappedComponent, props);
    },
);

// Safe inline: the input keeps its state across re-renders.
<Field name="search" label="Search" middleware={[withAnalytics("search")]} />
```

Called outside a field, a middleware from `createMiddleware` uses the settings it was made with.

### Example: dependent field fetch

A complete middleware that fetches data when another field changes — for instance, loading cities when a country is selected:

```typescript
import { createElement, useState, useEffect } from "react";
import { useFormContext } from "react-hook-form";
import type { Middleware, Option } from "@canonical/react-ds-global-form";

interface FetchRelatedOptions {
  /** API endpoint to fetch from */
  endpoint: string;
  /** Name of the field to watch for changes */
  watchField: string;
  /** Prop name to inject the fetched data into (default: "options") */
  targetProp?: string;
  /** Transform the raw API response into the shape the input expects */
  transformData?: (data: any) => Option[];
}

function addFetchRelated(options: FetchRelatedOptions): Middleware<any> {
  const {
    endpoint,
    watchField,
    targetProp = "options",
    transformData = (data) => data,
  } = options;

  return (WrappedComponent) => {
    return function FetchRelatedComponent(props) {
      const [data, setData] = useState<Option[] | null>(null);
      const [loading, setLoading] = useState(false);
      const [error, setError] = useState<string | null>(null);

      // Watch the other field's value via form context
      const { watch } = useFormContext();
      const watchValue = watch(watchField);

      useEffect(() => {
        // Reset when the watched field is empty
        if (!watchValue) {
          setData(null);
          return;
        }

        // Abort controller for cleanup on unmount or re-fetch
        const controller = new AbortController();
        setLoading(true);
        setError(null);

        fetch(
          `${endpoint}?${watchField}=${encodeURIComponent(watchValue)}`,
          { signal: controller.signal },
        )
          .then((response) => {
            if (!response.ok) throw new Error("Failed to fetch");
            return response.json();
          })
          .then((json) => {
            setData(transformData(json));
            setLoading(false);
          })
          .catch((err) => {
            if (err.name !== "AbortError") {
              setError(err.message);
              setLoading(false);
            }
          });

        // Abort the in-flight request if the watched value changes
        return () => controller.abort();
      }, [watchValue]);

      if (loading) {
        return createElement("div", null, "Loading...");
      }
      if (error) {
        return createElement("div", null, `Error: ${error}`);
      }

      // Inject the fetched data as a prop on the wrapped component
      return createElement(WrappedComponent, {
        ...props,
        [targetProp]: data,
      });
    };
  };
}
```

Usage — a city select that populates when the country field changes:

```tsx
<Field name="country" inputType="select" label="Country"
  options={[
    { value: "gb", label: "United Kingdom" },
    { value: "fr", label: "France" },
  ]}
/>

<Field
  name="city"
  inputType="select"
  label="City"
  options={[]}
  middleware={[
    addFetchRelated({
      endpoint: "/api/cities",
      watchField: "country",
      targetProp: "options",
      transformData: (data) =>
        data.cities.map((c) => ({ value: c.id, label: c.name })),
    }),
  ]}
/>
```

### Debouncing API calls

Any middleware that makes API calls on value changes should debounce to avoid flooding the server, and abort the request in flight when the value changes, so a slow answer for an old value cannot overwrite the answer for the new one. A timer and an `AbortController` in one effect do both, and the effect's cleanup cancels them when the value changes or the field unmounts:

```typescript
import { type ComponentType, createElement, useEffect } from "react";
import { useFormContext, useWatch } from "react-hook-form";
import type { BaseInputProps } from "@canonical/react-ds-global-form";

function withDebouncedValidation(url: string, wait = 300) {
  return <Props extends BaseInputProps>(
    WrappedComponent: ComponentType<Props>,
  ) =>
    function DebouncedComponent(props: Props) {
      const { name } = props;
      const { setError, clearErrors, getFieldState } = useFormContext();
      const value: unknown = useWatch({ name });

      useEffect(() => {
        if (typeof value !== "string" || value.length < 3) return;
        const requestUrl = `${url}?value=${encodeURIComponent(value)}`;
        const controller = new AbortController();
        const timer = setTimeout(async () => {
          try {
            const response = await fetch(requestUrl, { signal: controller.signal });
            if (controller.signal.aborted) return;
            if (!response.ok) {
              setError(name, { type: "remote", message: "Validation failed" });
            } else if (getFieldState(name).error?.type === "remote") {
              // Clear only the error this middleware set.
              clearErrors(name);
            }
          } catch {
            // Aborted, or the request failed: it says nothing about the value.
          }
        }, wait);
        return () => {
          clearTimeout(timer);
          controller.abort();
        };
      }, [value, name, setError, clearErrors, getFieldState]);

      return createElement(WrappedComponent, props);
    };
}
```

## Why masking is not middleware

A recurring idea is a `withMask` (or `addMask`) middleware, shared by the phone field and, say, a credit-card field. It does not work, and it is worth knowing why before reaching for it again.

Formatting a value is really two halves:

- **parse** — turning what the user typed into what the form stores (`"(555) 123-4567"` → `"5551234567"`).
- **format** — turning the stored value into what is displayed, on every keystroke, and putting the caret back where the user left it.

Middleware can do the first half. It can inject `registerProps`, so `setValueAs` normalises the submitted value. It cannot do the second: `value` and `onChange` are created by `bindField` *below* it, and the caret needs the DOM element, which no middleware ever receives. `setValueAs` is also a `register()`-path transform, so it does not run at all for a field bound `controlled`.

A middleware that does half the job is worse than none, because it looks like it works — the submitted value is correct — while the display half has to live somewhere else entirely.

There is a second, structural reason. Middleware is a chain: any number compose, in any order. Caret ownership is exclusive — two masking layers would fight over the same selection. Something that may only ever be applied once is not middleware, it is a strategy.

So the split is:

| Concern | Where it belongs |
| --- | --- |
| Effects, async work, injected props | Middleware |
| Normalising the submitted value | `createFormatterRegisterOptions`, or the component's own change handler |
| Display projection and caret | `useFormattedValue` |

Use `useFormattedValue` with a `Formatter` — a `{ format, parse }` pair of pure functions, both exported from the package root — for anything where the string on screen differs from the string submitted. `createPatternFormatter("(###) ###-####")` covers fixed grouping; because `format` is an ordinary function, it can also pick its grouping from the value itself, which is what a card number needs (American Express groups 4-6-5 where most brands group 4-4-4-4). Pair it with `inputType="custom"` for a field this package does not ship.

## Composing multiple middleware

When a field needs several middleware, pass them as an array. The composition order matters — the first middleware in the array is the outermost wrapper:

```tsx
<Field
  name="product"
  inputType="combobox"
  label="Product"
  options={[]}
  middleware={[
    withAnalytics("product-search"),   // Outermost — sees all props
    addRESTOptions("/api/products"),    // Middle — injects options
    withDebouncedValidation("/api/v"), // Innermost — closest to input
  ]}
/>
```

Each middleware receives the component returned by the next one. This means outer middleware can observe props set by inner middleware, but not vice versa.

## Type safety

For middleware that only works with specific input types, use a narrow type parameter instead of `any`:

```typescript
import type { Middleware } from "@canonical/react-ds-global-form";

// This interface matches what Select and Combobox expect
interface WithOptions {
  options: Array<{ value: string; label: string }>;
  name: string;
}

// TypeScript enforces that this middleware is only used
// with components that accept an options prop
function withSortedOptions(): Middleware<WithOptions> {
  return (WrappedComponent) => {
    return function SortedComponent(props: WithOptions) {
      const sorted = [...props.options].sort((a, b) =>
        a.label.localeCompare(b.label),
      );
      return createElement(WrappedComponent, {
        ...props,
        options: sorted,
      });
    };
  };
}
```

Use `Middleware<any>` when the middleware works with any input type — this is the common case for middleware that only interacts with form context and does not touch input-specific props.
