# Messages and internationalization

Every word DataViews renders or announces comes from one record of messages. The record ships in English. An application rewords some of it, or replaces all of it with another language.

## One record

The record's type is `DataViewsMessages`, from `@canonical/dataviews-core`. It holds 121 messages: 68 are text and 53 are functions. They are grouped by the part that says them: the table's status, its selection and resize controls, its sort, its header and settings menus, what a change to the columns announces, the sort panel, the filters, the search, the pagination bar, the saved views, the action bar, the charts and the renderer switch. Each member's TSDoc says what it names.

The English record is the default. A message the application does not give keeps its English.

## The root's `messages` prop

`DataViews` takes `messages`. Every connected part inside the root reads the root's words, so the parts take no `messages` of their own.

Give a **partial set** to reword a few messages. The rest stay English:

```tsx
import type { DataViewsMessages } from "@canonical/dataviews-core";
import { DataViews } from "@canonical/dataviews-react";

// At module scope, so the record keeps one identity.
const OWN_WORDS: Partial<DataViewsMessages> = {
  search: "Find a machine",
  statusNoResults: "No machine matches this search.",
  pageCount: (pages) => `of ${pages} ${pages === 1 ? "screen" : "screens"}`,
};

export function Machines({ provider }: { readonly provider: MachineProvider }) {
  return (
    <DataViews provider={provider} messages={OWN_WORDS}>
      <DataViews.Search />
      <DataViews.DataTable columns={columns} label="Machines" />
      <DataViews.Pagination sizes={[5, 10]} />
    </DataViews>
  );
}
```

Give a **whole replacement** to translate. Annotate it as `DataViewsMessages`, not `Partial<DataViewsMessages>`. Then a missing message fails to compile, and a message added to the record in a later release fails to compile until you translate it:

```ts
import type { DataViewsMessages } from "@canonical/dataviews-core";

export const FRENCH: DataViewsMessages = {
  statusPending: "Chargement…",
  // … every other message
};
```

The package's tests check that a whole replacement leaves no English, both in the server's markup and once scripts run: `src/testing/integration/a-whole-replacement-leaves-no-english.test.tsx`.

Three rules about the record you pass:

- A message given as `undefined` is left out, so it keeps its English. A catalog that has not loaded yet, or a lookup that missed, does not blank a control's name.
- The root holds the record while its members stay the same. Strings written inline cost nothing. A function written inline is a new function on every render, and every part that reads it renders again. Define the record once, at module scope or held by the application.
- The resolved record is frozen. No part can reword another part's messages.

## Standalone parts

A standalone part is its own root, so it takes `messages` itself. `DataTable` and `PaginationBar` do, and so do the work-in-progress `DataCards` and `DataChart`:

```tsx
<DataTable provider={provider} columns={columns} label="Machines" messages={FRENCH} />
<PaginationBar provider={provider} messages={FRENCH} />
```

Inside a root, the connected twins (`DataViews.DataTable`, `DataViews.Pagination`) take the root's words instead.

## Messages that state a fact

A message that states a fact is a function of that fact. The part calls it with the fact, and the message words it:

| Message | Called with | English |
| --- | --- | --- |
| `selectRow` | the row's name | `Select alpha` |
| `statusFailed` | the reason | `These rows could not be loaded: the inventory is offline` |
| `deselectRows` | a count | `Deselect 3 rows` |
| `pageCount` | a count | `of 1 page`, `of 12 pages` |
| `rowsShown` | the first row, how many show, and the total as a `Count` | `Showing 1–5 out of 12 rows` |
| `sortPrecedence` | a direction, a position and a total | `ascending, 2nd of 3` |
| `columnMoved` | a column's name, its position and how many show | `Host moved to position 2 of 4` |
| `filterRefused` | every reason, and whether the earlier restriction still applies | `Must be a number. The previous restriction still applies.` |
| `viewPending` | the saved-view command | `Saving…` |

How the facts are passed:

- One fact per argument, the subject first. For a saved-view message, the command comes first.
- An object only where the core already has that record: the `Count` that `rowsShown` and `facetCount` take is `exact`, `at-least`, or (for `rowsShown`) `unknown`.
- A list of like facts as an array, such as the reasons `sortRefused` takes.
- A name is placed where the message puts it and never altered. It may stand for a column heading drawn as an element, not as text.

**Plurals and ordinals are the message's own to word.** The parts pass numbers, never words like "row" or "rows". The English record chooses its forms through `Intl.PluralRules("en")`, its ordinals (`1st`, `2nd`, `3rd`) through `Intl.PluralRules("en", { type: "ordinal" })`, and groups its numbers through `Intl.NumberFormat("en")`. A translation uses its own language's rules.

**Reasons come from elsewhere.** A reason is a short lowercase fragment from the source, the schema or the store, such as `the machine inventory could not be reached`. The record places it and does not translate it. The core's own reasons, such as those `createArraySource` gives, are English. A source you write can give its reasons in the reader's language. Each refusal also carries a machine-readable `code`.

## `resolveMessages`

`resolveMessages(messages)`, from `@canonical/dataviews-core/bindings`, is what a root does with its `messages`: it returns the whole record, the given messages over English, frozen, with `undefined` members left out. Called with nothing, it returns the English record.

```ts
import { resolveMessages } from "@canonical/dataviews-core/bindings";

const english = resolveMessages();
const words = resolveMessages({ search: "Find a machine" });
words.search; // "Find a machine"
words.page; // "Page"
```

A renderer of your own uses it to speak the same words: see **_work_in_progress / DataViews / Renderers / Build your own renderer**.

## Labels are data, not messages

The record holds the library's words. It does not hold the names of the application's data:

- field labels, given to `DataViews.Filters` as `labels`;
- column headings, given to `DataTable` as each column's `header`;
- the values a field holds, and so the options a filter lists;
- the names the application gives a region, such as a table's `label`, or the renderers a switch offers.

Translate these where you declare them. In the French story below, the column headings and the field labels are the application's own French.

## The announcer

Each `DataViews` root renders one polite live region after its children (`aria-live="polite"`, `aria-relevant="additions"`). It draws nothing. A standalone `DataTable` renders its own region after the table.

It says outcomes that have no place on screen:

- the ordering now in force, after a heading, its menu or the sort panel changes it (`sortApplied`, `sortDefaulted`, `sortAbsent`);
- why a sort changed nothing (`sortRefused`);
- a column hidden, shown or moved, with its new position (`columnHidden`, `columnShown`, `columnMoved`), a column that cannot be hidden (`columnAlwaysShown`), and the table's settings reset (`tableSettingsReset`).

It does not say what a place on screen already says. The table's status, the pagination summary, a filter's feedback and the saved views' status each speak from their own element, and the announcer stays silent, so a reader hears each outcome once.

How it speaks:

- Messages said within 100 ms are spoken as one announcement. In that moment the same text is said once.
- An outcome with one latest answer, such as the ordering, replaces what was waiting under the same topic.
- Each announcement leaves the region 7 seconds after it was spoken.
- A second root over the same provider has its own region and says nothing of the first root's commands.

The announcer's words come from the same record as everything else.

## Translating

A whole locale is a `DataViewsMessages` record written in the language. This French record chooses its plurals with `Intl.PluralRules("fr")`, in which 0 and 1 take the singular, its ordinals with `Intl.PluralRules("fr", { type: "ordinal" })` (`1er`, `2e`), and groups its numbers with `Intl.NumberFormat("fr")`:

Mark the language of the region where the record speaks, with `lang`. The package sets no `lang` of its own:

```tsx
<div lang="fr">
  <DataViews provider={provider} messages={FRENCH}>
    <DataViews.Search />
    <DataViews.Filters labels={{ status: "État", cores: "Cœurs" }} />
    <DataViews.DataTable columns={frenchColumns} label="Machines" selectable />

</div>
```

## Right-to-left text

The stylesheets place and space things with logical properties (`padding-inline`, `inset-inline`, `text-align: start`), so the layout follows the page's direction. Three things do not:

- The resize handle reads the keys and the pointer physically: Right Arrow widens a column and Left Arrow narrows it, in either direction.
- `moveColumnLeft` and `moveColumnRight`, and their named forms, move a column one place earlier or later in the order. Word them for that effect in a right-to-left language.
- No message isolates the names it places. A name written in another direction can reorder the text around it. A locale can isolate names itself, in its own functions, with the Unicode isolates U+2068 and U+2069:

```ts
const isolate = (name: string): string => `⁨${name}⁩`;

const ARABIC: DataViewsMessages = {
  // …
  selectRow: (name) => `تحديد ${isolate(name)}`,
  // …
};
```
