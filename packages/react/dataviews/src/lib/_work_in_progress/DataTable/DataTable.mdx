# DataTable recipes

`DataTable` renders the rows of one collection and nothing else: it does not fetch, own the URL or decide where views persist. A provider owns the collection's query, result and selection and drives the source that answers it; the table observes the provider and shows what it holds. Each recipe below is the smallest complete code for one job, followed by the live story that shows it.

The table is dense wherever it sits: the table within its frame carries the design system's `.dense` class, and its rows and cells take their height and padding from the density channel of `@canonical/styles`, so load that stylesheet on the page. Its sort chevrons and checkbox marks are `@canonical/ds-assets` icons, which the page serves at `/icons`, as for every other design-system icon.

## A table over a provider

Declare the collection once, at module scope: its fields, and the identity every record carries. It is the witness the provider is built over and every hook is handed, and the record type is inferred from `identify`, so nothing is spelled twice. Then build the provider once, in state, over the collection and its source. Building it starts nothing: the table observes the provider for as long as it is mounted, and the first observer runs the source and asks for the first page. From then on every sort, search or page change issues its own request, and the last observer to leave stops it all. The source declares what it can filter and sort, the provider reads that declaration, and the table offers only what the source can run.

```tsx
import {
  createArraySource,
  createCollection,
  createDataViewsProvider,
} from "@canonical/dataviews-core";
import { createColumns, DataTable } from "@canonical/dataviews-react";
import { useState } from "react";
import { type Machine, machines } from "./machines.js";

// Declared once, beside the records it describes.
export const machineCollection = createCollection({
  identify: (machine: Machine) => machine.id,
  fields: [
    { field: "status", kind: "choices", options: ["running", "failed", "pending"] },
    { field: "cores", kind: "number", min: 1 },
    { field: "name", kind: "text" },
    { field: "owner", kind: "text" },
  ],
});

const columns = createColumns(machineCollection, [
  { field: "name", header: "Host" },
  { field: "status", header: "Status" },
  { field: "owner", header: "Owner" },
]);

export function Machines() {
  // Built once: the table observes it, which starts its source.
  const [provider] = useState(() =>
    createDataViewsProvider({
      collection: machineCollection,
      source: createArraySource({
        rows: machines,
        collection: machineCollection,
        searchFields: ["name", "owner"],
      }),
    }),
  );
  return <DataTable provider={provider} columns={columns} label="Machines" />;
}
```

Every column names the record field it shows, and its id is that field's name unless two columns show one field and one is given an `id`. Primitive values render as text, and anything else needs a cell renderer.

## Columns and sizing

The recipes from here on keep the provider built above and change only the columns.

A column is `fixed` — it keeps exactly its width — or `flex`: it takes at least its `minPx`, at most its `maxPx`, and a share of whatever is left by `weight`. The solver reserves every fixed width and every minimum first, then shares the rest; a column that reaches its maximum hands its excess back to the others. When even the reservations do not fit, nothing is squeezed: the table scrolls. The one exception is the last column, which takes whatever width the columns before it leave — past its own maximum or fixed width when there is room to spare — so the table never ends in a gap.

```tsx
import { createColumns, DataTable } from "@canonical/dataviews-react";
import { machineCollection } from "./machines.js";

const columns = createColumns(machineCollection, [
  { field: "name", header: "Host", sizing: { kind: "flex", weight: 2, minPx: 160 } },
  { field: "status", header: "Status", sizing: { kind: "fixed", px: 112 } },
  { field: "region", header: "Region", sizing: { kind: "flex", weight: 1, minPx: 96, maxPx: 144 } },
  { field: "cores", header: "Cores", sizing: { kind: "fixed", px: 80 } },
  { field: "owner", header: "Owner", sizing: { kind: "flex", weight: 1, minPx: 96 } },
]);

<DataTable provider={provider} columns={columns} label="Machines" />;
```

## Sorting

Mark a column `sortable` and the table offers the order, but only when the source declares that field sortable: the provider carries the source's declaration, and a `sortable` column on a field outside it offers nothing, because a heading offering a sort the source would refuse would be a control that does nothing. Activating a heading sorts by that column alone and cycles ascending, descending, then back to the source's own order. Shift with a click, Enter or Space adds the column as a further term instead, turns an ascending term descending where it stands, and removes a descending one; a term past what the source orders by changes nothing, and the heading says why, politely. Focus stays on the heading throughout.

The headings show the ordering in force — the reader's own terms, or the source's documented default when there are none — so rows a source orders are never shown as unsorted. Each heading the ordering names shows a chevron, up for ascending and down for descending, and from two terms a numeral for its place; its control is described by both, as "descending, 2nd of 3". Exactly one heading, the first term's, carries `aria-sort`. Once scripts run, a menu beside each heading sorts it ascending or descending — in place when the column is already ordered, as a further term while the source has room, and alone once it has none — or removes it from the reader's ordering, where the column offers sorting; it also hides the column, unless it is declared `hideable: false` or is the last one shown, and moves it left or right past the column beside it. Choosing an item returns focus to its button, or to the heading now standing where a hidden column stood, and the table announces a hide or a move with the column's new position. Without scripting each sortable heading is a real link to the next ordering, from the first page, where the provider has a location to lead to.

```tsx
import { createColumns, DataTable } from "@canonical/dataviews-react";
import { machineCollection } from "./machines.js";

const columns = createColumns(machineCollection, [
  { field: "name", header: "Host", sortable: true },
  { field: "status", header: "Status", sortable: true },
  { field: "region", header: "Region" },
  { field: "cores", header: "Cores", sortable: true },
  { field: "owner", header: "Owner" },
]);

<DataTable provider={provider} columns={columns} label="Machines" />;
```

To open on an order, issue it once the provider is built, before anything observes it: `provider.setSort([{ field: "status", direction: "asc" }])` inside the state initializer. The first request then carries it.

## Selection

`selectable` adds a leading 32px column of the design system's `CheckboxInput`, backed by the provider's selection; the column's width is the stylesheet's, and the data columns share what it leaves. Name each record with `rowLabel`, so a checkbox says which machine it selects rather than which position it holds — the row is typed as the collection's record, so its fields need no cast. The header checkbox acts on the rows the reader can see, and leaves a selection made on another page alone.

```tsx
import { createColumns, DataTable } from "@canonical/dataviews-react";
import { machineCollection } from "./machines.js";

const columns = createColumns(machineCollection, [
  { field: "name", header: "Host" },
  { field: "status", header: "Status" },
  { field: "owner", header: "Owner" },
]);

<DataTable
  provider={provider}
  columns={columns}
  label="Machines"
  selectable
  rowLabel={(row) => row.name}
/>;
```

## Records of several types

A collection whose records come in several types declares them on one `choices` field, its `discriminator`, and scopes a field to the types that carry it with `appliesTo`. A cell for a field that does not apply to the row's type draws a dash and reads "Not applicable" — a third state beside a value and an empty one — and the column's heading is described by the types it applies to, read but not drawn. A column may narrow its field's scope further with its own `appliesTo`, checked where the table mounts. Columns declared through `createColumns` hand their `cell` the record at its own type, so content narrows on the discriminator and the compiler holds the arms exhaustive. A page carrying a record of a type the collection does not declare is refused visibly, and the status names the row and the type.

## Selection on touch

The checkbox is the selection's baseline path everywhere. On touch, a long press on a row selects it and puts the table in selection mode, where a tap on a row toggles it; a tap on one of the row's own controls — its checkbox, a link in a cell — is that control's alone. Deselecting the last row ends the mode. Entering and leaving are announced through the messages record (`selectionModeEntered`, `selectionModeEnded`), and the mode is stated on the table as `data-selection-mode="true"` while it holds, so a stylesheet may select it by attribute. A row's own selected state is its `aria-selected`, with no class repeating it.

## A warning past the render ceiling

A table rendering every row of a large window works, and says so in development: past 500 rows without `virtualization`, it warns once, naming the count and pointing to `virtualizeRows` from `@canonical/dataviews-react/virtualization`. It is a prompt to measure and never a cap — every row the viewer asked for is still rendered, and a production build says nothing. The cards renderer warns at the same count, saying it has no virtualization to opt into.

## Row headers

Declare one column `rowHeader` and its cell is the row's header: a reader hears its text before each of the row's other cells, the row is named by it, and so is the row's selection checkbox unless `rowLabel` names the row — a row whose header shows no text falls back to its identity. A table has at most one; a second fails where the table mounts. The row header is never hidden, whatever it declares, since hiding it would take the row's name with it.

```tsx
import { createColumns, DataTable } from "@canonical/dataviews-react";
import { machineCollection } from "./machines.js";

const columns = createColumns(machineCollection, [
  { field: "name", header: "Host", rowHeader: true },
  { field: "status", header: "Status" },
]);

<DataTable provider={provider} columns={columns} label="Machines" selectable />;
```

## The frame and its footer

The table stands in a frame, which is the caller's box: `className`, `style`, `ref` and the other native props land there, and a height capped on it scrolls the table within while the header sticks. The frame's `footer` holds the pagination bar beneath the table and outside the table role — a landmark, never a row — and keeps it to the bottom of the view while a tall table scrolls past. A standalone table's live region sits in the frame after the footer. The connected `DataViews.DataTable` places `DataViews.Pagination` in the footer unless given another, or `null` for none.

```tsx
import { DataTable, PaginationBar } from "@canonical/dataviews-react";

<DataTable
  provider={provider}
  columns={columns}
  label="Machines"
  style={{ maxBlockSize: "60vh" }}
  footer={<PaginationBar provider={provider} sizes={[10, 25, 50]} />}
/>;
```

## Resizing and its limits

`resizable` puts a control on a column's trailing edge, driven by the pointer or the keyboard — arrow keys step the edge, Escape abandons a drag. Every resize is held to the column's declared `minPx` and `maxPx`, however often it has been resized, and a column widened past the container scrolls the table so the edge being moved stays in view.

The last column never gets a control, even when it is declared `resizable`: its trailing edge is the table's own edge, with nothing beyond it to resize against. It takes whatever width the others leave instead. Two tables on one provider read one presentation, the provider's, so a resize in either is the arrangement of both and nothing is passed between them; the presentation also holds the column order and which columns are hidden, and a column may declare `hideable: false` to stay in every arrangement.

```tsx
import { createColumns, DataTable } from "@canonical/dataviews-react";
import { machineCollection } from "./machines.js";

const columns = createColumns(machineCollection, [
  { field: "name", header: "Host", resizable: true, sizing: { kind: "flex", weight: 1, minPx: 120, maxPx: 320 } },
  { field: "region", header: "Region", resizable: true, sizing: { kind: "flex", weight: 1, minPx: 96, maxPx: 160 } },
  { field: "status", header: "Status", sizing: { kind: "fixed", px: 112 } },
  { field: "owner", header: "Owner", sizing: { kind: "flex", weight: 1, minPx: 96 } },
]);

<DataTable provider={provider} columns={columns} label="Machines" />;
```

## A cell that reads its own scope

A column's `cell` renderer runs inside its cell's scope, so it can read the row's channels with `useDataViewsCell` — the whole record, another field, or the row's selection — without the table handing every cell a copy of the record. The hook takes the collection as its witness: it checks, at runtime, that the table's provider was built over that very collection, and in return the record arrives typed as the collection's record, with no cast at the call site. Because the collection lives at module scope, so does the cell; it is declared once, for every table over the collection. It re-renders when its channels change, and nothing else does.

```tsx
import {
  createColumns,
  DataTable,
  type DisplayFieldCellProps,
  useDataViewsCell,
  useDataViewsValue,
} from "@canonical/dataviews-react";
import { machineCollection } from "./machines.js";

function HostCell({ value }: DisplayFieldCellProps) {
  // The collection is the witness: the record is typed as a machine.
  const { record, selected } = useDataViewsCell(machineCollection);
  const { owner } = useDataViewsValue(record);
  const isSelected = useDataViewsValue(selected);
  return (
    <span
      style={{
        fontWeight: isSelected
          ? "var(--typography-text-primary-bold-font-weight)"
          : undefined,
      }}
    >
      {String(value)}
      <span style={{ color: "var(--color-text-muted)" }}> ({owner})</span>
    </span>
  );
}

const columns = createColumns(machineCollection, [
  { field: "name", header: "Host", cell: HostCell },
  { field: "status", header: "Status" },
]);

<DataTable
  provider={provider}
  columns={columns}
  label="Machines"
  selectable
  rowLabel={(row) => row.name}
/>;
```

## The outcomes

A table with no rows says why, and the reasons stay distinct: nothing has arrived yet (`pending`), the read failed (`failed`), the collection is empty (`no-data`), or the query matched nothing (`no-results`). They call for different responses from the reader — wait, retry, add something, change the query — so they are never collapsed into one message.

Two more are said *above* rows rather than in place of them, because a table that keeps showing rows must not hide what went wrong: `refresh-failed`, where the rows still answer the query but the request that would have replaced them failed, and `stale`, where an earlier query produced them. The status is the core's `DisplayStatus`, decided once from the collection's state; the table renders it and decides nothing itself. A settled outcome is announced once as a polite status message, a passing state is silent. `renderStatus` replaces the default text with your own words; the stories below show the defaults.

```tsx
import type { DisplayStatus } from "@canonical/dataviews-core";
import { createColumns, DataTable } from "@canonical/dataviews-react";
import { machineCollection } from "./machines.js";

const columns = createColumns(machineCollection, [
  { field: "name", header: "Host" },
  { field: "status", header: "Status" },
]);

const statusText = (status: DisplayStatus): string => {
  switch (status.status) {
    case "pending":
      return "Fetching machines…";
    case "regrouping":
      return "Regrouping machines…";
    case "failed":
      return `Could not read machines: ${status.reason}`;
    case "refresh-failed":
      return `These machines could not be refreshed: ${status.reason}`;
    case "stale":
      return `These machines do not match the current search: ${status.reason}`;
    case "no-data":
      return "No machines are enrolled yet.";
    case "no-results":
      return "No machines match this search.";
  }
};

<DataTable
  provider={provider}
  columns={columns}
  label="Machines"
  renderStatus={statusText}
/>;
```

## Mounting only the rows in view

A table renders every row of its result window, which is the right default: a page of fifty is small, and every row is in the page for the browser's own search and for a reader without JavaScript. When a result window holds thousands of rows, give the table `virtualization`, and it mounts only the rows near its viewport. `virtualizeRows` comes from its own entry point, `@canonical/dataviews-react/virtualization`, so an application that never imports it never ships it. The window the provider starts on is in its `snapshot`.

```tsx
import {
  createArraySource,
  createDataViewsProvider,
} from "@canonical/dataviews-core";
import { createColumns, DataTable } from "@canonical/dataviews-react";
import { virtualizeRows } from "@canonical/dataviews-react/virtualization";
import { useState } from "react";
import { machineCollection, machines } from "./machines.js";

// One descriptor serves any number of tables: each keeps its own
// viewport, measurements and focus.
const virtualization = virtualizeRows({ estimatedRowHeight: 24 });

const columns = createColumns(machineCollection, [
  { field: "name", header: "Host", sortable: true },
  { field: "status", header: "Status", sortable: true },
  { field: "owner", header: "Owner" },
]);

export function Machines() {
  const [provider] = useState(() =>
    createDataViewsProvider({
      collection: machineCollection,
      source: createArraySource({
        rows: machines,
        collection: machineCollection,
        searchFields: ["name", "owner"],
      }),
      // Every machine in one window.
      snapshot: { query: "page=1&size=10000", presentation: {} },
    }),
  );
  return (
    <DataTable
      provider={provider}
      columns={columns}
      label="Machines"
      virtualization={virtualization}
      style={{ maxBlockSize: "24rem" }}
    />
  );
}
```

- **Give the table its height.** The table becomes its own scroll viewport, with the header held above its rows. It is no taller than the screen unless a height capped on its frame says otherwise; a table as tall as its content would mount every row.
- **The estimate is only an estimate.** `estimatedRowHeight` places a row until it is mounted, and then the row is measured. Rows may differ in height: a cell that wraps grows its row, and the rows around it make room. When a row above the viewport turns out taller than estimated, the view stays on the rows being read.
- **Every row still counts.** The table reports how many rows it has and each mounted row its position among them, so assistive technology knows there is more above and below. Selection, the header's select-all and sorting act on every row of the result window, mounted or not.
- **Focus stays put.** The row holding focus stays mounted however far the table scrolls, with a neighbour on each side, and is let go when focus leaves the table.
- **What it does not do.** Rows that are not mounted are not in the page, so the browser's own search does not find them. On the server, and without JavaScript, the table renders its whole result window, and paging is what keeps that bounded: keep real page links for readers without JavaScript. Hydrating that markup costs what hydrating a table without `virtualization` costs, before the table narrows to the rows in view.
