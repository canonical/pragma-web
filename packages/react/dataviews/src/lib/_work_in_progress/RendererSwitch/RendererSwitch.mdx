# RendererSwitch recipes

`RendererSwitch` shows one collection through the renderer a reader chooses. The application places the renderers — a table, a second table with fewer columns, cards — and gives each an id, a name and its content; the switch offers them in the design system's select and draws the one chosen. The switch's own name comes from `messages`, over English, as a standalone part's does; the renderers are named by the application, as fields and options are. It is a work-in-progress spike: it is not exported from the package root, and its shape may change or it may be withdrawn.

## Switching renderers over one root

Every renderer the switch holds reads the same root, so they share one query, one set of rows and one selection. A machine selected in the table is still selected when the reader chooses the summary, and choosing a renderer asks the source for nothing.

```tsx
import {
  createArraySource,
  createDataViewsProvider,
} from "@canonical/dataviews-core";
import { DataViews, type DataTableColumn } from "@canonical/dataviews-react";
import { useState } from "react";
import { machineCollection, machines } from "./machines.js";
// A work-in-progress spike: not yet exported from the package root.
import { RendererSwitch } from "./RendererSwitch.js";

const detailColumns: readonly DataTableColumn[] = [
  { id: "name", header: "Host" },
  { id: "status", header: "Status" },
  { id: "cores", header: "Cores" },
];

const summaryColumns: readonly DataTableColumn[] = [
  { id: "name", header: "Host" },
  { id: "status", header: "Status" },
];

export function Machines() {
  const [provider] = useState(() =>
    createDataViewsProvider({
      collection: machineCollection,
      source: createArraySource({ rows: machines, collection: machineCollection }),
    }),
  );
  return (
    <DataViews provider={provider}>
      <RendererSwitch
        label="Show machines as"
        renderers={[
          {
            id: "table",
            label: "Table",
            content: <DataViews.DataTable columns={detailColumns} label="Machines" selectable />,
          },
          {
            id: "summary",
            label: "Summary",
            content: <DataViews.DataTable columns={summaryColumns} label="Machines, summarised" selectable />,
          },
        ]}
      />
    </DataViews>
  );
}
```

## The choice is the switch's own

The switch holds the chosen renderer while it is mounted, and the first renderer until another is chosen. The choice does not reach the provider, the URL or a saved view: reloading the page, opening a link or opening a saved view shows the first renderer again. Whether a renderer choice should be remembered, and where, is still an open question, so nothing here decides it.

## Without scripting

Without scripting there is nothing to choose a renderer with, so the switch offers no select and draws the first renderer — the default — alone, in a region named for it, with its own baseline: the table's sort links and native checkboxes, the pagination bar's forms. Drawing every renderer would repeat each record's checkboxes, links and status in one page, and checkboxes named alike would post twice once selection posts. Once scripts run, the select appears over the same renderer, and the others are offered from it.

## What the spike found

The switch knows no choice before it draws: the choice is its own state, and nothing in the URL or a saved view carries it, so hydration always starts from the first renderer and nothing drawn by the server is thrown away. A renderer choice the switch could know before it draws would let the server draw another; that persistence is the open question this spike does not settle.
